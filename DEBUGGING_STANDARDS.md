# Marius Command Center — AI Operating Standards
Read this file FIRST, before touching any code, data, or docs in this repo.
This replaces the old `DEBUGGING_STANDARDS.md` — same purpose, wider scope.

Zia (the owner) is a non-coder, browser-only, no terminal. Your job is
smooth, uninterrupted pipeline flow with minimal demands on his time. Act,
don't ask, unless you've hit a wall you genuinely can't get past yourself.

## The three living docs in this repo — know the difference
- `STATUS.md` — auto-generated by a GitHub Actions bot on every "update
  status" commit. **Never hand-edit this.** It's a live snapshot, not a
  narrative.
- `CONTINUATION.md` — the human-readable handoff. Update this yourself at
  the end of a session with what changed and what's still open. This is
  what the next session reads to pick up where you left off.
- `DEBUGGING_STANDARDS.md` (this file) — how to behave, not what happened.
  Rarely changes. If you're tempted to log today's specific bug here,
  it belongs in `CONTINUATION.md` instead.

Don't create a fourth doc, a dated log file, or a "v2" of anything. If a
doc needs updating, edit it in place. This repo has already accumulated
and cleaned up one pile of abandoned duplicate logs — don't start a new one.

## Standing behavioral rules
1. **Verify live before stating anything as fact.** Supabase `status`
   columns can be stale. GitHub Actions' green tick does not mean real
   work happened — check row counts, storage objects, or the actual
   YouTube channel. Don't infer from filenames, comments, or a doc's
   prior claims without re-checking.
2. **Trace root cause in the actual code**, not from symptoms alone. Read
   the function. Cross-check against live data. Look for evidence that
   contradicts your leading theory before committing to it. If a fix
   doesn't hold under a real retry (see the content-flagged case in
   `CONTINUATION.md` for a worked example — text-level fix worked for one
   script, didn't for two others, and that gap mattered), say so plainly
   instead of declaring victory early.
3. **Minimize Zia's involvement, but don't fake progress to do it.** Use
   GitHub/Supabase tools yourself to check state, diagnose, and fix
   end-to-end. Only involve Zia for: (a) something requiring his literal
   click/paste because GitHub write is 403'd for the AI connector, or
   (b) a decision that's genuinely his to make (spending money, changing
   what the channel covers, deleting something irreversible). Don't ask
   permission for routine fixes that keep the pipeline moving — do them,
   then report what you did.
4. **When you can't push code directly** (confirmed 403 on
   `create_or_update_file` / `push_files` for this repo), give the exact
   `.../edit/main/<path>` URL in its own copy block, then the full file
   content in a chat code block. Never tell Zia to find or edit a specific
   line — always full-file replace. Deletions are simpler: trash icon on
   the file's page, no paste needed.
5. **Data-only fixes don't need a GitHub paste at all.** If the fix is
   rewording a shot's `visual_description`, resetting a `status` column,
   or similar, just do it directly via Supabase. Reserve the paste
   workflow for actual code changes.
6. **One copyable thing per code block.** URLs, paths, IDs, secrets —
   each in its own block, never combined, never inline in prose.
7. **Say what you don't know.** If you can't access Actions run logs
   (confirmed: no such tool exists in the current toolset — don't
   re-search for one every session) or can't reach an external API
   (Agnes AI is unreachable from the sandbox — confirmed), say so and ask
   for the one specific piece of information you're missing, rather than
   guessing and presenting it as confirmed.
8. **This repo is public** — GitHub Actions minutes are uncapped here (the
   2,000 min/month limit only applies to private repos). Don't hold back
   a scheduling/frequency change over a minutes budget that doesn't apply.
   Gemini/Supabase's own rate limits are the real constraints to watch.

## Before ending any session
Update `CONTINUATION.md` with: what changed, what's confirmed live-working,
what's still open/unverified, and the concrete next step. Don't write a
new file to do this — edit the existing one.
